## 1. Introduction

### 1.1 Purpose

This document specifies the functional and non-functional requirements of a
personal portfolio website. The intended audience is anyone who needs to
understand what the system does before reading the design (SDD) or the code:
future maintainers, collaborators, and AI agents that may be asked to modify
the site.

### 1.2 Scope

The product is a **single-page, static portfolio website** that presents the
author's profile, skills, projects, and experience to recruiters and other
visitors. It runs entirely in the visitor's browser — there is no server-side
logic, no database, and no user accounts.

The project is **out of scope** for this specification: any backend services,
contact form with server submission, blog/CMS, analytics collection, and
multi-language support. These may appear in a future version (see SDD §7).

### 1.3 Definitions

| Term | Meaning |
|------|---------|
| Hero | The first full-screen section of the page (name + intro + terminal) |
| Terminal | The interactive fake-shell widget in the hero section |
| Event stream | The auto-updating demo feed of simulated SOC events |
| Gacha flip | The card-reveal animation that rotates project cards over the vertical (Y) axis |
| Sanitized | Work content described without internal identifiers (no internal IPs, tool names, or company details) |

## 2. Overall Description

### 2.1 Product Perspective

The system is a standalone static site. It consists of one HTML page, one
stylesheet, one script file, and a set of static assets (resume PDF,
placeholder project images). There is no build step and no dependency
framework; the only external dependency is Google Fonts.

### 2.2 User Classes

| Class | Description | Needs |
|-------|-------------|-------|
| Recruiter / hiring manager | Primary target. Skims to decide whether to contact the author. | Clear identity, skills, projects, and contact info above the fold; fast load on mobile |
| Developer / technical peer | Evaluates code quality and implementation. | Readable source in the public repo; sensible structure |
| General visitor | Lands via link or search. | Readable content without interaction |

### 2.3 Operating Environment

- **Client:** modern evergreen browsers (Chrome, Edge, Firefox, Safari),
  desktop and mobile (min width 375 px).
- **Hosting:** any static host; current deployment is Vercel.
- **No** local software, server, or network requirement beyond the page's
  own assets and the font CDN.

### 2.4 Constraints

- No JavaScript frameworks or libraries (vanilla JS only).
- No backend, no database, no build tooling.
- All personal content must be sanitized where it relates to employment.
- Page must remain lightweight (static assets, no heavy media).

### 2.5 Assumptions and Dependencies

- The visitor's browser supports ES2020+, CSS Grid, and
  `IntersectionObserver`.
- The resume PDF in `assets/` is current; it is a build-time asset, not
  generated by the site.
- Fonts are served by Google Fonts CDN; if unreachable, the site falls back
  to system fonts and remains functional.

## 3. Requirements

### 3.1 Functional Requirements

| ID | Requirement |
|----|-------------|
| F1 | **Navigation.** A fixed top nav shows site links (Skills, Projects, Experience, Contact). On viewports ≤ 720 px it collapses to a hamburger toggle that opens/closes the link list. Clicking a link scrolls to the section and closes the menu on mobile. |
| F2 | **Interactive terminal.** The hero contains a terminal widget that types an intro sequence (`whoami`) character-by-character on load. The user may type commands. Supported commands: `help`, `whoami`, `skills`, `projects`, `contact`, `clear`. Unknown commands return a "command not found" message. Output is typed with a blinking block cursor; commands are queued if entered while output is still typing. |
| F3 | **Demo event stream.** A panel in the hero displays a feed of simulated SOC events (time, host, event type, detail). A new row is prepended every ~2.4 s; the list is capped at 7 rows. Simulated "alert" event types are visually highlighted. The feed is explicitly labelled **demo data**. |
| F4 | **Project cards.** The Projects section shows three project cards (SOC Investigation Tools, MCP Tool Orchestration Server, Tomato Leaf Disease Detection). Each card shows a media area (animated process-chain demo or placeholder image), title, description, and technology tags. Cards are revealed with a Y-axis flip animation (card back shows "?"), staggered in sequence. |
| F5 | **Section title animation.** Each section heading (Skills, Projects, Experience, Contact) is typed out character-by-character when it first scrolls into view, then settles to the final styled title without any layout shift. |
| F6 | **Resume download.** A "Download Resume" button links to `assets/resume.pdf` and triggers a browser download. |
| F7 | **Contact links.** Email, GitHub, and LinkedIn links are present in the hero and Contact section, opening the respective destinations. A "Email Me" button uses a `mailto:` link. |
| F8 | **Skills display.** Skills are shown as grouped tag chips (Security, Programming, Web & Database, Tools) in a responsive grid. |
| F9 | **Experience timeline.** Experience entries (role, organization, dates, bullet points) are rendered as a vertical timeline. |

### 3.2 Non-Functional Requirements

| ID | Requirement |
|----|-------------|
| NF1 | **Responsiveness.** Layout must work from 375 px (mobile) to desktop with no horizontal overflow. The hero switches from two-column to single-column below 860 px. |
| NF2 | **Performance.** The page must be static and load without any build or server step. No third-party JS. Total page weight must stay small (no large raster media); animations must be CSS/GPU-friendly. |
| NF3 | **Accessibility & motion.** When the visitor's OS requests reduced motion (`prefers-reduced-motion: reduce`), all entrance/flip/typing animations are disabled and content appears immediately. Semantic HTML headings and list markup are used. |
| NF4 | **Information hygiene.** No internal network addresses, company-internal tool names, or unpublished work details may appear in the site or its source. Internal projects are described in sanitized form and labelled as such. |
| NF5 | **Maintainability.** Content (text, links, projects) must be editable by editing a small number of clearly-structured files without changing the animation logic. |

### 3.3 External Interface Requirements

| ID | Interface |
|----|-----------|
| E1 | Browser rendering (HTML/CSS/JS). |
| E2 | Google Fonts CDN (Inter, JetBrains Mono) with system-font fallback. |
| E3 | GitHub (public repo `SyahWZ/portfoliosyahmi`) as the source of truth. |
| E4 | Vercel as the deployment target; root URL rewrites to `portfolio.html` via `vercel.json`. |
